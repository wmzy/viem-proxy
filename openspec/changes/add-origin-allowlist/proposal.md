# Change: Add Origin Allowlist (ALLOWED_ORIGINS)

## Why
The `API_KEY` is a server-side secret: a browser frontend embedding a self-deployed instance cannot keep one (any visitor can extract it from the bundle), so authentication is useless against browser-originated abuse, and a per-IP rate limit only slows it down. Browser requests are self-identifying, though — cross-origin calls and same-origin POSTs carry an `Origin` header, while server-side/mobile callers never do. An `ALLOWED_ORIGINS` env var turns that into an Origin-level guard: browser requests from non-allowlisted origins are rejected at the door, non-browser callers are unaffected. When the allowlist is set, the CORS layer must also be tightened to match (echo the matched origin instead of `*`); otherwise disallowed origins' preflights would still pass with `Access-Control-Allow-Origin: *`. Finally, the product's privacy-relevant behaviors (GET URLs in intermediary logs, cross-user cache sharing, no key custody, API_KEY's server-side-only scope) deserve explicit user-facing disclosure.

## What Changes
- New `workers/src/utils/origin.ts`: `parseOriginAllowlist` (unset/empty → `null` = feature off; comma-separated hosts; `scheme://` prefixes stripped, ports honored, lowercased; `*.example.com` wildcards match the apex **and** all subdomains — excluding the apex would silently break the main site while adding no security, since anyone controlling a subdomain controls that origin), `matchOrigin` (host-based, port-sensitive; unparseable origins like the sandboxed-iframe literal `null` match nothing), `ORIGIN_CHECK_EXEMPT_PATHS` (`/dashboard` only)
- Fail-closed semantics: an allowlist that parses to zero rules (e.g. `", ,"`) rejects **all** Origin-carrying requests — same philosophy as `ALLOWED_CHAIN_IDS`, a broken allowlist must never silently widen access
- New middleware in `workers/src/index.ts` on `*`, registered after the trace middleware (so 403s carry `X-Trace-Id`/`X-Cache`) and **before** rate limiting and auth (browser abuse is cheapest to stop at the door): `ALLOWED_ORIGINS` unset → no-op (zero behavior change); set → an Origin-carrying request must match or gets `403` with `{ code: -32000, message: "Origin not allowed" }` and no CORS echo; requests without Origin pass through and stay protected by `API_KEY` + rate limiting. Exemptions: only `/dashboard` (unauthenticated, read-only operator page, needed most during a flood — decision documented in code and README). `/api/v1/stats` and `/api/v1/health` are deliberately **not** exempt: browsers reach them from allowlisted domains or not at all. 403s never touch upstreams or Durable Objects, and are not recorded in statistics (the reject is a config decision, not proxied work)
- CORS tightening in `workers/src/index.ts`: hono's `cors()` takes static options but the rules come from env, so the middleware is built per env value and cached per isolate keyed by the raw var (constant per isolate). Unset → identical to the previous static `origin: "*"` config; set → `Access-Control-Allow-Origin` echoes the matched request origin verbatim (plus `Vary: Origin`), and non-matching or absent origins get no ACAO header at all — so actual responses and preflight `OPTIONS` from outside the allowlist are both rejected by browsers before any proxied work
- `ALLOWED_ORIGINS` added to `Env` (`workers/src/types.ts`), a commented sample in `workers/wrangler.toml`, and a `cloudflare.bindings` description in `workers/package.json` (shown on the one-click deploy page)
- README: new「Origin 白名单（浏览器场景防护）」section (semantics, ordering, exemptions, fail-closed) + `ALLOWED_ORIGINS` line in the manual-deploy `wrangler.toml` sample; new「🔒 隐私与数据披露」section disclosing ① GET URLs carry addresses/calldata into CDN/proxy logs, ② cache is shared across users for identical parameters, ③ the server stores no private keys, never signs, proxies read-only methods only and keeps only aggregate statistics, ④ API_KEY is server-side-only — browser callers should use `ALLOWED_ORIGINS`

## Impact
- Affected specs: `workers-backend` (new requirements)
- Affected code:
  - `workers/src/utils/origin.ts` — new: `OriginRule`, `ORIGIN_CHECK_EXEMPT_PATHS`, `parseOriginAllowlist`, `matchOrigin`
  - `workers/src/index.ts` — env-aware CORS assembly (cached per isolate) + origin-check middleware (after trace, before rate-limit/auth)
  - `workers/src/types.ts`, `workers/wrangler.toml`, `workers/package.json`
  - `workers/test/handlers.test.ts` — new "Origin allowlist (app-level)" describe
  - `README.md` — Origin 白名单 + 隐私与数据披露 sections
- No breaking changes: `ALLOWED_ORIGINS` unset preserves all current behavior exactly (full existing suite green, plus an explicit zero-drift regression test); setting it only adds 403s for non-allowlisted browser origins
- Out of scope (deliberately): rate-limit logic and its exemption set (untouched), auth semantics, health-endpoint reporting of the new knob
